### How They(Lambda and functional interface) Connect (The "Aha!" Moment)
A Lambda expression cannot exist on its own in Java. A Lambda expression is simply a shortcut to implement the single abstract method of a Functional Interface.

Whenever you write a lambda, Java looks at the target Functional Interface and says, "Ah, they are providing the code for that one missing method."
```java
@FunctionalInterface
public interface MathOperation {
    // The ONE abstract method
    int calculate(int a, int b); 
    
    // Default methods are perfectly fine!
    default void printInfo() {
        System.out.println("This is a math operation.");
    }
}
```

The "Trick" Question: Interviewers will ask, "Can a Functional Interface have more than one method?" The answer is Yes. It can have as many default or static methods (which have implementations) as it wants, but it can only have one abstract method.

The Old Way (Anonymous Inner Class):
Before Java 8, if you wanted to implement an interface on the fly without creating a whole new separate class file, you had to write a massive, ugly block of boilerplate code:

```java
MathOperation addition = new MathOperation() {
    @Override
    public int calculate(int a, int b) {
        return a + b;
    }
};

System.out.println(addition.calculate(5, 3)); // Outputs: 8
```
The Lambda Way:
Because MathOperation only has one abstract method, Java already knows the method name is calculate, it knows it takes two ints, and it knows it returns an int. You don't need to type all that out. You just provide the lambda:
```java
// (a, b) are the inputs -> (a + b) is the return value
MathOperation addition = (a, b) -> a + b; 

System.out.println(addition.calculate(5, 3)); // Outputs: 8
```
![alt text](<009java 8 interfaces_240517_134527_250714_011514_6.jpg>) 
When you write `Consumer<Integer> obj`, you are telling the Java compiler to replace that generic `<T>` with `<Integer>`.

If you didn't specify `<Integer>`, Java wouldn't know what kind of data your lambda expression is allowed to process. It needs to know the input type so it can enforce strict rules and give you autocomplete features in your IDE.

```java
// 1. We declare a Consumer that TAKES an Integer (and returns void)
Consumer<Integer> addTenAndPrint = (num) -> {
    System.out.println(num + 10);
};

// 2. We pass an Integer into it
addTenAndPrint.accept(5); // Outputs: 15
```
Because you wrote `<Integer>`, Java knows that the variable num inside your lambda is definitely an Integer. If you tried to do addTenAndPrint.accept("Hello"), the code wouldn't even compile, saving you from a crash.

Whenever you see the < > brackets in Java, remember that they are just filling in the blanks (the Ts and Rs) in the original interface design.

Q--> tell me what is different in direct function call like f() and then this ()->{f()}??

1. The Direct Call: f() (Immediate Execution)
When you write f(), you are telling the JVM: "Stop whatever you are doing, go execute the code inside f(), and give me the result right this second."

If you pass a direct function call as an argument to another method, Java must execute f() completely before it can even step inside the outer method.


```java
// Java executes calculateHeavyMath() IMMEDIATELY.
// If it takes 10 seconds to run, your program freezes here for 10 seconds.
// Then, it passes the result into the printResult method.
printResult(calculateHeavyMath());
```
2. The Lambda Call: () -> { f() } (Deferred Execution)
When you write () -> { f() }, you are not calling the function. You are wrapping the function call inside an object (like a Supplier or Runnable).

You are telling the JVM: "Do not run f() right now. Just package it up into a set of instructions so I can pass it around."

```java
// Java DOES NOT execute calculateHeavyMath() here.
// It takes 0 seconds. It just hands the "instructions" to the printResult method.
printResult(() -> { calculateHeavyMath(); });
```
inside the printResult method, that heavy math function will only execute if the method explicitly calls .get() or .run() on your lambda. If printResult decides it doesn't need the math after all, calculateHeavyMath() is never executed, saving you massive amounts of CPU time.

So here we have transferred the responsibility to call `calculateHeavyMath(); ` to `printResult()`.By wrapping the call in () -> { f() }, you are saying to printResult(): "Here is the remote control. You decide if, when, and how many times to press the button."

To make this completely click, here is what the inside of that printResult method actually looks like. Notice how it is entirely up to printResult to decide if the heavy math runs or not:

```java
// It receives the lambda as a Supplier
public void printResult(boolean condition, Supplier<Integer> mathRecipe) {
    
    if (condition == true) {
        // The condition is met! 
        // THIS is the exact moment calculateHeavyMath() actually executes.
        Integer result = mathRecipe.get(); 
        System.out.println("The result is: " + result);
    } else {
        // The condition is false.
        // We do nothing. calculateHeavyMath() is NEVER executed. 
        // We just saved a massive amount of CPU time!
        System.out.println("We didn't need the math today.");
    }
}
```
This exact transfer of responsibility is the secret engine behind almost everything in modern Java, including the Streams API, Spring Boot's @Transactional annotations, and Java's multithreading.


### The Summary Rule
* **`Supplier`** has `get()`
* **`Consumer`** has `accept()`
* **`Function`** has `apply()`
* **`Predicate`** has `test()`

Whenever you pass a lambda to a Java method, Java takes your lambda body and invisibly pastes it inside whichever of those four methods belongs to the interface.

## When a Class Implements Two Interfaces

If two interfaces have **different method names** — no conflict, both methods are simply implemented.

The interesting case is when **both interfaces have a method with the same name and signature**.

---

### Case 1 — Both Interfaces Have Different Methods (No Conflict)

```java
interface Printable {
    void print();
}

interface Scannable {
    void scan();
}

class Machine implements Printable, Scannable {

    @Override
    public void print() {
        System.out.println("Printing...");
    }

    @Override
    public void scan() {
        System.out.println("Scanning...");
    }
}

public class Main {
    public static void main(String[] args) {
        Machine m = new Machine();
        m.print(); // "Printing..."
        m.scan();  // "Scanning..."
    }
}
```

No issue here — both interface methods are implemented separately and both work fine.

---

### Case 2 — Both Interfaces Have the SAME Method Signature

```java
interface A {
    void show();
}

interface B {
    void show();
}

class MyClass implements A, B {

    // Only ONE implementation needed for both
    @Override
    public void show() {
        System.out.println("show() from MyClass");
    }
}

public class Main {
    public static void main(String[] args) {

        MyClass obj = new MyClass();
        obj.show(); // "show() from MyClass"

        // Called via Interface A reference
        A a = new MyClass();
        a.show(); // "show() from MyClass"

        // Called via Interface B reference
        B b = new MyClass();
        b.show(); // "show() from MyClass"
    }
}
```

**Answer: The class's own implementation is called every time — regardless of which interface reference you use.**

Java does not care which interface the method came from. Since the class provides one single `show()`, that is always what gets executed.

---

### Case 3 — Both Interfaces Have DEFAULT Methods with the Same Name (The Real Conflict)

This is where Java actually forces you to resolve the conflict:

```java
interface A {
    default void greet() {
        System.out.println("Hello from A");
    }
}

interface B {
    default void greet() {
        System.out.println("Hello from B");
    }
}

// COMPILE ERROR if you don't override greet()
class MyClass implements A, B {

    @Override
    public void greet() {
        // You MUST override and decide what to do
        System.out.println("Hello from MyClass");

        // You can also explicitly call a specific interface's default:
        A.super.greet(); // "Hello from A"
        B.super.greet(); // "Hello from B"
    }
}

public class Main {
    public static void main(String[] args) {
        MyClass obj = new MyClass();
        obj.greet();
        // Output:
        // Hello from MyClass
        // Hello from A
        // Hello from B
    }
}
```

If you do NOT override `greet()` in `MyClass`, Java throws a **compile-time error** because it cannot decide between A's and B's default implementation.

---

### Summary Table

| Scenario | What happens |
|---|---|
| Different method names | Both implemented separately, no conflict |
| Same method name, no default | Class writes one implementation, that is always called |
| Same default method in both interfaces | Compile error — you must override in the class |
| Same default method, override in class | Class's own version is called |
| Want specific interface's default | Use `A.super.greet()` inside the class |

---

### The Golden Rule

**The class's own implementation always wins.** If the class overrides the method, that is what gets called — no matter which interface reference you use to call it. The interface only defines the contract; the class decides the behaviour.

# Java and "Multiple Inheritance" — The Interface Default Method Wrinkle

## The Classic Statement

"Java doesn't support multiple inheritance" is true **for classes** — a class can only `extends` **one** superclass:
```java
class C extends A, B { }  // ❌ compile error, not allowed
```

But Java **does** allow a class to `implement` **multiple interfaces**:
```java
class C implements A, B { }  // ✅ totally fine
```

Before Java 8, this distinction was clean because interfaces could only declare abstract methods (no bodies) — so there was no actual *behavior* being inherited, just contracts. No ambiguity possible.

## Java 8 Changed the Game: Default Methods

Java 8 introduced `default` methods — interfaces can now have method **bodies**:
```java
interface A {
    default void greet() {
        System.out.println("Hello from A");
    }
}

interface B {
    default void greet() {
        System.out.println("Hello from B");
    }
}
```

Now if a class implements **both**:
```java
class C implements A, B {
    // must override greet(), or this won't compile!
}
```

This is exactly the classic **"diamond problem"** that multiple class inheritance famously causes in languages like C++ — if `C` implements both `A` and `B`, and both provide a default `greet()`, **which one does `C` inherit?**

## How Java Resolves This

Java doesn't pick one for you — it **forces you to resolve the ambiguity explicitly**. If you don't, you get a **compile-time error**:

```java
class C implements A, B { }
```
```
error: class C inherits unrelated defaults for greet() from types A and B
```

You are **required** to override the method in `C` and decide what should happen:

```java
class C implements A, B {
    @Override
    public void greet() {
        // Option 1: pick one explicitly
        A.super.greet();   // calls A's version specifically

        // Option 2: pick the other
        // B.super.greet();

        // Option 3: write completely new behavior
        // System.out.println("Hello from C");

        // Option 4: combine both
        A.super.greet();
        B.super.greet();
    }
}
```

The `InterfaceName.super.methodName()` syntax is special — it's the **only** way in Java to explicitly call a specific interface's default implementation, disambiguating which "version" you want.

## Important Nuance: This Rule Only Triggers on Actual Conflict

If only **one** of the interfaces provides a default implementation, there's no ambiguity, and Java doesn't force an override:

```java
interface A {
    default void greet() {
        System.out.println("Hello from A");
    }
}

interface B {
    void greet();   // abstract, no default
}

class C implements A, B {
    // ✅ compiles fine — inherits A's default automatically, no conflict
}
```

The conflict rule specifically applies when **two or more interfaces provide competing default implementations for the same method signature**.

## What About Class + Interface Conflicts?

There's actually a clear **priority rule** here, sometimes called the "**class wins**" rule:

```java
class Parent {
    void greet() {
        System.out.println("Hello from Parent class");
    }
}

interface A {
    default void greet() {
        System.out.println("Hello from A interface");
    }
}

class C extends Parent implements A {
    // no conflict — Parent's class method wins automatically, no error
}
```

**Rule of thumb, in order of priority:**
1. A method from a **superclass** always wins over an interface's `default` method — no ambiguity, no compiler complaint.
2. A **more specific interface** (one that extends another) wins over a less specific one.
3. If neither rule resolves it (e.g., two unrelated interfaces both with the same default method), it's a **conflict**, and the implementing class **must** override and resolve it manually.

## Why Java Designed It This Way

This design deliberately **avoids the true diamond problem** that plagues languages with full multiple inheritance (like C++), where ambiguous inheritance can be silently resolved by the compiler in ways that surprise the programmer. Java's philosophy:

> If there's genuine ambiguity in behavior, **force the programmer to decide explicitly** rather than picking an implicit "winner" that might not be what they intended.

This is why Java is often described as supporting **multiple inheritance of *type* (interfaces) and *default behavior***, but **not multiple inheritance of *state*** (instance fields) — interfaces still cannot have instance fields (only `static final` constants), so there's no possibility of the "which parent's field do I use?" ambiguity that plagues true multiple inheritance in other languages.

## Summary Table

| Situation | Compiles? | Resolution |
|---|---|---|
| Two interfaces, only one has a `default` method | ✅ Yes | Automatically inherits the one default |
| Two interfaces, both have conflicting `default` methods for same signature | ❌ No (unless overridden) | Must explicitly override using `InterfaceName.super.method()` |
| Superclass method vs. interface default method (same signature) | ✅ Yes | Superclass method always wins, no override needed |
| Two interfaces, one extends the other, both have defaults for same method | ✅ Yes | The more specific (subinterface's) default wins automatically |

So the accurate statement is: **Java doesn't support multiple inheritance of implementation from classes, but it does allow multiple interface inheritance — and when that creates a genuine conflict via default methods, the compiler forces you to resolve it explicitly rather than guessing.**

## Applications


 Many **Java built-in classes** internally use Consumer and Supplier. 

---

## Classes that use `Consumer<T>`

### 1. `Iterable` / `Collection` — `forEach()`
```java
// ArrayList, LinkedList, Set, etc.
List<String> list = List.of("A", "B", "C");
list.forEach(s -> System.out.println(s));
//           ^^^^^^^^^^^^^^^^^^^^^^^^^^^ Consumer<String>
```

### 2. `Stream` — `peek()` and `forEach()`
```java
Stream.of(1, 2, 3)
    .peek(n -> System.out.println("Before: " + n))  // Consumer - for debugging
    .map(n -> n * 2)
    .forEach(n -> System.out.println("After: " + n)); // Consumer
```

### 3. `Map` — `forEach()`
```java
Map<String, Integer> scores = Map.of("Alice", 90, "Bob", 85);
scores.forEach((name, score) ->                    // BiConsumer<String, Integer>
    System.out.println(name + " scored " + score)
);
```

### 4. `Optional` — `ifPresent()` and `ifPresentOrElse()`
```java
Optional<String> opt = Optional.of("Hello");
opt.ifPresent(val -> System.out.println(val));     // Consumer<String>

opt.ifPresentOrElse(
    val -> System.out.println("Found: " + val),    // Consumer - if value exists
    ()  -> System.out.println("Empty!")            // Runnable - if empty
);
```

### 5. `CompletableFuture` — `thenAccept()`
```java
CompletableFuture.supplyAsync(() -> fetchData())
    .thenAccept(data -> saveToDatabase(data));  // Consumer - process result
//              ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ runs after future completes
```

---

## Classes that use `Supplier<T>`

### 1. `Optional` — `orElseGet()` and `orElseThrow()`
```java
Optional<User> opt = userRepo.findById(id);

// Supplier called ONLY if Optional is empty
User user = opt.orElseGet(() -> new User("guest"));       // Supplier<User>

// Supplier called ONLY if Optional is empty
User user2 = opt.orElseThrow(() -> new RuntimeException("Not found")); // Supplier<Exception>
```

### 2. `CompletableFuture` — `supplyAsync()`
```java
// Supplier provides the value asynchronously
CompletableFuture<String> future = 
    CompletableFuture.supplyAsync(() -> callExternalAPI()); // Supplier<String>
```

### 3. `Objects` — `requireNonNullElseGet()`
```java
// Supplier only called if first arg is null
String name = Objects.requireNonNullElseGet(nullableName, 
                () -> "default");  // Supplier<String>
```

### 4. `Logger` (SLF4J / Log4j2) — Lazy log messages
```java
// Bad - string always built even if DEBUG is off
logger.debug("User data: " + heavyObject.toString());

// Good - Supplier, only called if DEBUG level is enabled ✅
logger.debug(() -> "User data: " + heavyObject.toString()); // Supplier<String>
```

### 5. `Stream` — `generate()`
```java
// Supplier keeps producing values infinitely
Stream.generate(() -> Math.random())   // Supplier<Double>
      .limit(5)
      .forEach(System.out::println);

// Generate UUIDs
Stream.generate(UUID::randomUUID)      // Supplier<UUID>
      .limit(3)
      .collect(Collectors.toList());
```

## Real-World Example — Both Together

```java
// A generic cache class using both
public class Cache<T> {
    private T value;

    // Supplier fetches data if cache is empty
    public T getOrLoad(Supplier<T> loader) {
        if (value == null) {
            value = loader.get();        // Supplier used here
        }
        return value;
    }

    // Consumer processes cached data
    public void process(Consumer<T> action) {
        if (value != null) {
            action.accept(value);        // Consumer used here
        }
    }
}

// Usage:
Cache<List<User>> cache = new Cache<>();
cache.getOrLoad(() -> userService.fetchAllUsers());  // Supplier
cache.process(users -> users.forEach(System.out::println)); // Consumer
```
