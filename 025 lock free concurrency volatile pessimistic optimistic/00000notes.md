
## Compare and Swap (CAS) in Java

---

### The Problem First — Why Do We Need This?

```java
// Two threads running this simultaneously
int counter = 0;
counter++;  // THIS IS NOT THREAD SAFE!

// counter++ is actually 3 steps:
// 1. READ  counter value (0)
// 2. ADD   1 to it      (1)
// 3. WRITE back         (1)

// Thread 1: READ  → 0
// Thread 2: READ  → 0   ← reads BEFORE Thread 1 writes!
// Thread 1: WRITE → 1
// Thread 2: WRITE → 1   ← overwrites Thread 1's result!
// Expected: 2,  Got: 1  ❌
```

**Solutions:**
- `synchronized` — works but **slow** (blocks all other threads)
- `volatile` — ensures visibility but **not atomicity**
- `AtomicInteger` — **fast + thread safe** ✅ using CAS

---

### What is Compare and Swap (CAS)?

CAS is a **hardware-level CPU instruction** that does 3 things **atomically** (as one uninterruptible operation):

```
CAS(variable, expectedValue, newValue)

1. LOOK at the current value
2. COMPARE it with expectedValue
3. If they MATCH  → SWAP with newValue → return true
   If they DON'T  → do nothing         → return false
```

All 3 steps happen as **one atomic CPU instruction** — no thread can interrupt in between.

---

### Visual — How CAS Works

```
Thread 1 wants to change counter: 0 → 1

STEP 1: Read current value
        Memory: [0]
        Thread 1 expects: 0

STEP 2: Compare
        current(0) == expected(0) ✅ MATCH!

STEP 3: Swap
        Memory: [0] → [1]
        Returns: true ✅


─────────────────────────────────────────

Thread 2 ALSO wants to change counter: 0 → 1
(But Thread 1 already changed it to 1)

STEP 1: Read current value
        Memory: [1]
        Thread 2 expects: 0

STEP 2: Compare
        current(1) == expected(0) ❌ NO MATCH!

STEP 3: Do nothing, RETRY
        Memory: [1]  unchanged
        Returns: false → retry with new expected value
```

---

## What is CAS?

CAS is a **CPU-level atomic instruction**. It does 3 things in a single uninterruptible operation:

```
CAS(memoryLocation, expectedValue, newValue)
```

1. **Read** the value at `memoryLocation`
2. **Compare** it with `expectedValue`
3. **Swap** with `newValue` only if they match — otherwise do nothing

---

## How Does a Thread "Expect" a Value?

Before calling CAS, the thread **reads the current value first**, then uses that as its expected value:

```java
int expected = atomicVar.get();      // Step 1: thread reads current value (say 5)
int newValue = expected + 1;         // Step 2: thread computes new value (6)
atomicVar.compareAndSet(expected, newValue);  // Step 3: CAS(5, 6)
```

So the thread is saying:
> *"I read 5 a moment ago. If it's STILL 5, change it to 6. If someone else changed it, don't touch it."*

---

## Visual: Two Threads Racing

```
Memory: [5]

Thread A reads → expects 5, wants to write 6
Thread B reads → expects 5, wants to write 6

Thread A wins the race:
  CAS(5, 6) → memory is 5? YES → write 6 ✅
  Memory: [6]

Thread B arrives late:
  CAS(5, 6) → memory is 5? NO (it's 6) → do nothing ❌
  Thread B must RETRY → reads 6, expects 6, wants to write 7
  CAS(6, 7) → memory is 6? YES → write 7 ✅
```

---

## This is Why It's Called "Optimistic Locking"

| | Synchronized (Pessimistic) | CAS (Optimistic) |
|---|---|---|
| Assumption | Conflict WILL happen | Conflict is RARE |
| Strategy | Lock first, then work | Work first, retry if failed |
| Threads blocked? | Yes | No — they spin/retry |
| OS involvement | Yes (context switch) | No — pure CPU instruction |

## In Java — Under the Hood

```java
AtomicInteger counter = new AtomicInteger(5);

// This internally does CAS in a loop:
counter.incrementAndGet();
```

Internally it looks like this:

```java
// Simplified JDK source
int current;
do {
    current = get();           // read current value
} while (!compareAndSet(current, current + 1));  // retry until success
```

The loop keeps retrying until the CAS succeeds — this is called a **spin loop**.

---

## At the CPU Level

CAS maps directly to a **single CPU instruction**:
- x86: `CMPXCHG`
- ARM: `LDREX / STREX`

The CPU **locks the memory bus** for just that one instruction — far cheaper than an OS-level mutex lock.

---

## The One Famous Problem: ABA

```
Memory: [A]

Thread 1 reads → expects A
Thread 2 changes A → B → A  (back to A!)
Thread 1 does CAS(A, newVal) → sees A → SUCCESS ✅ (but value secretly changed!)
```

Thread 1 thinks nothing changed, but it actually did. Java solves this with **`AtomicStampedReference`** which tracks a **version number** alongside the value:

```java
// CAS checks BOTH value AND stamp (version)
AtomicStampedReference<Integer> ref = new AtomicStampedReference<>(5, 0);
ref.compareAndSet(5, 6, 0, 1);  // (expectedVal, newVal, expectedStamp, newStamp)
```

---

## Summary

```
1. Thread reads current value → this becomes "expected"
2. Thread computes new value
3. CAS checks: is memory STILL == expected?
   ├── YES → swap atomically ✅
   └── NO  → someone else changed it, retry from step 1 ❌
```

The "expectation" is simply **the value the thread read just before attempting the swap** — CAS ensures no one sneaked in between the read and the write.


### AtomicInteger — Most Common

```java
import java.util.concurrent.atomic.AtomicInteger;

AtomicInteger counter = new AtomicInteger(0);

// Basic operations
counter.get();                  // read value → 0
counter.set(10);                // set value  → 10
counter.getAndIncrement();      // return THEN increment (i++)
counter.incrementAndGet();      // increment THEN return (++i)
counter.getAndDecrement();      // return THEN decrement
counter.getAndAdd(5);           // return THEN add 5
counter.addAndGet(5);           // add 5 THEN return

// THE CAS operation directly
boolean success = counter.compareAndSet(10, 20);
// if current == 10, set to 20, return true
// if current != 10, do nothing, return false
```

---

### How incrementAndGet() Works Internally

```java
// What Java actually does under the hood:
public int incrementAndGet() {
    while (true) {                          // keep retrying
        int current  = get();               // step 1: read
        int next     = current + 1;         // step 2: calculate
        if (compareAndSet(current, next))   // step 3: CAS
            return next;                    // success!
        // if CAS failed → another thread changed it → retry
    }
}

// Example with 2 threads:
// Thread1: current=0, next=1, CAS(0,1) ✅ → returns 1
// Thread2: current=0, next=1, CAS(0,1) ❌ (already 1!) → retry
//          current=1, next=2, CAS(1,2) ✅ → returns 2
```

This loop is called a **spin loop** or **optimistic locking**.

### synchronized vs Atomic — Key Difference

```java
// synchronized — PESSIMISTIC locking
// "Someone MIGHT interfere, so I'll LOCK everyone out"
synchronized(this) {
    counter++;   // only one thread at a time
}
// Other threads BLOCK and WAIT 🔴

// ─────────────────────────────────────────

// Atomic CAS — OPTIMISTIC locking
// "Interference is RARE, I'll try and retry if needed"
atomicCounter.incrementAndGet();
// Other threads DON'T block — they retry 🟢
```

| | `synchronized` | `Atomic` (CAS) |
|---|---|---|
| Strategy | Pessimistic | Optimistic |
| Other threads | Block & wait | Retry |
| Overhead | High (lock/unlock) | Low (CPU instruction) |
| Best for | High contention | Low-medium contention |
| Scope | Block of code | Single variable |

### ABA Problem — CAS Weakness

```java
// CAS only checks VALUE, not how many times it changed!

// Thread 1 reads:  A (value=10)
// Thread 2 changes: A→B→A  (10→20→10)
// Thread 1 CAS:   expects A(10), sees A(10) ✅ 
//                 BUT the value changed in between!

// Fix: AtomicStampedReference — tracks VERSION too
AtomicStampedReference<Integer> ref =
    new AtomicStampedReference<>(10, 0);  // value=10, stamp=0

int[] stamp = new int[1];
int value = ref.get(stamp);         // get value AND stamp

// CAS checks BOTH value AND stamp
ref.compareAndSet(10, 20, stamp[0], stamp[0] + 1);
//               old  new  oldStamp   newStamp
// Even if value is same, stamp will differ → detects ABA ✅
```

### Summary

```
CAS = Compare And Swap
    = One atomic CPU instruction
    = Read + Compare + Write  (uninterruptible)

AtomicInteger   → thread-safe int
AtomicBoolean   → thread-safe boolean  
AtomicLong      → thread-safe long
AtomicReference → thread-safe object reference

All use CAS internally:
  → No locks
  → No blocking
  → Just retry if someone else changed the value first
```

> **CAS is the foundation of all lock-free, non-blocking thread-safe operations in Java.** It trades blocking for retrying — which is much faster when contention is low.

## Optimistic vs Pessimistic Locking Strategy

---

### Real World Analogy First

```
PESSIMISTIC — Like a bathroom with a lock:
  "Someone WILL try to come in, so I'll LOCK the door first"
  → Others WAIT outside until you're done
  → Safe but causes waiting

OPTIMISTIC — Like a whiteboard in an office:
  "Nobody is probably writing at the same time as me"
  → Just write, but CHECK if someone else wrote before you save
  → If they did → erase and redo your work
  → Fast but may need retrying
```

---

### Pessimistic Strategy

**Assumption:** Conflicts WILL happen → prevent them upfront by locking.

```java
// Thread 1 acquires the lock
synchronized(this) {
    // Thread 2, 3, 4... all BLOCKED here waiting 🔴
    int value = counter;     // read
    value = value + 1;       // modify
    counter = value;         // write
}
// Thread 1 releases lock → Thread 2 gets it → Thread 3 waits...
```

### How It Works Step by Step

```
Thread 1: ACQUIRE LOCK ────────────────── RELEASE LOCK
               ↓                               ↓
Thread 2: ──── BLOCKED ──── BLOCKED ──── ACQUIRE LOCK ── RELEASE
                                                    ↓
Thread 3: ──────────────── BLOCKED ────────────────── ACQUIRE...


Timeline:
[T1 works] → [T2 works] → [T3 works]   ← sequential, one by one
```

---

### Optimistic Strategy

**Assumption:** Conflicts are RARE → don't lock, just verify before saving.

```java
// No lock at all — just try and retry if needed
while (true) {
    int current = atomicCounter.get();      // 1. READ current value
    int next    = current + 1;              // 2. CALCULATE new value
    
    if (atomicCounter.compareAndSet(current, next)) {
        break;                              // 3. SUCCESS → done ✅
    }
    // CAS failed → someone else changed it → RETRY 🔄
}
```

### How It Works Step by Step

```
Thread 1: READ(0) → CALCULATE(1) → CAS(0→1) ✅ DONE
Thread 2: READ(0) → CALCULATE(1) → CAS FAIL ❌ (value is now 1)
          READ(1) → CALCULATE(2) → CAS(1→2) ✅ DONE
Thread 3: READ(0) → CALCULATE(1) → CAS FAIL ❌
          READ(2) → CALCULATE(3) → CAS(2→3) ✅ DONE


Timeline:
[T1,T2,T3 all start together] → failures → retries → all finish
         ↑ parallel attempts, no waiting!
```

---

### Side by Side Comparison

```java
// ─────────────── PESSIMISTIC ───────────────
public synchronized void pessimisticIncrement() {
    counter++;      // safe, but others are BLOCKED
}

// ─────────────── OPTIMISTIC ────────────────
AtomicInteger atomicCounter = new AtomicInteger(0);

public void optimisticIncrement() {
    atomicCounter.incrementAndGet();  // safe, no blocking, may RETRY
}
```

---

### The Core Difference in Mindset

```
PESSIMISTIC:
  "I don't trust anyone. I'll lock first, work, then unlock."
  
  Lock → Work → Unlock
   ↓
  Others WAIT (blocked, doing nothing)


OPTIMISTIC:
  "I trust things are probably fine. I'll work freely,
   then just double-check before I commit."
   
  Work → Check → Commit (or Retry)
   ↓
  Others also WORK in parallel (no waiting)
```

---

### When Each Strategy Wins

#### Low Contention (few threads, rare conflicts)

```
OPTIMISTIC WINS ✅

Thread1: READ → WORK → CAS ✅  (rarely fails)
Thread2: READ → WORK → CAS ✅  (rarely fails)
Thread3: READ → WORK → CAS ✅  (rarely fails)

→ All succeed on first try, no waiting, very fast!

PESSIMISTIC here is wasteful:
→ You're locking "just in case" but conflicts never happen
→ Unnecessary overhead of acquiring/releasing locks
```

#### High Contention (many threads, frequent conflicts)

```
PESSIMISTIC WINS ✅

OPTIMISTIC here is wasteful:
Thread1: RETRY RETRY RETRY RETRY...  ← wasting CPU spinning
Thread2: RETRY RETRY RETRY RETRY...  ← wasting CPU spinning
Thread3: RETRY RETRY RETRY RETRY...  ← wasting CPU spinning

→ Too many retries = CPU burns doing useless work (spin waste)

PESSIMISTIC here is better:
→ Threads sleep while waiting (no CPU waste)
→ Orderly one-by-one execution
```

## Pessimistic Locking in Java

> **Lock the resource BEFORE doing work — nobody else can touch it**

---

### Using synchronized

```java
public class BankAccount {
    private int balance = 1000;

    // Lock acquired before method runs
    // Only 1 thread at a time
    public synchronized void withdraw(int amount) {
        // Thread-2 BLOCKED here until Thread-1 finishes
        if (balance >= amount) {
            balance -= amount;
            System.out.println("Withdrawn: " + amount
                + " | Balance: " + balance
                + " | Thread: " + Thread.currentThread().getName());
        }
    }
}
```

---

### Using ReentrantLock

```java
public class BankAccount {
    private int balance = 1000;
    private ReentrantLock lock = new ReentrantLock();

    public void withdraw(int amount) {
        lock.lock();  // ← LOCK FIRST — pessimistic
        try {
            // only 1 thread here at a time
            // others BLOCKED at lock.lock()
            if (balance >= amount) {
                balance -= amount;
                System.out.println("Withdrawn: " + amount
                    + " Balance: " + balance);
            }
        } finally {
            lock.unlock();  // always unlock
        }
    }
}
```

---

### What happens internally

```
Thread-1 → lock.lock()  → gets lock → enters
Thread-2 → lock.lock()  → BLOCKED — waits outside
Thread-3 → lock.lock()  → BLOCKED — waits outside

Thread-1 finishes → lock.unlock()
Thread-2 → gets lock → enters
Thread-3 → BLOCKED — waits

→ Strictly one at a time
→ No two threads ever work together
```

## Optimistic Locking in Java

> **Work without locking — but verify at the end using version/stamp**

---

### Using AtomicInteger — compareAndSet (CAS)

```java
public class BankAccount {

    // AtomicInteger uses CAS internally — optimistic locking
    private AtomicInteger balance = new AtomicInteger(1000);

    public void withdraw(int amount) {
        while (true) {
            int currentBalance = balance.get();      // read current value
            int newBalance = currentBalance - amount; // compute new value

            if (newBalance < 0) {
                System.out.println("Insufficient balance");
                return;
            }

            // compareAndSet = optimistic check
            // "only update if value is STILL what I read"
            // if another thread changed it → returns false → retry
            if (balance.compareAndSet(currentBalance, newBalance)) {
                // ✅ success — no one changed value between read and update
                System.out.println("Withdrawn: " + amount
                    + " Balance: " + newBalance);
                return;
            }
            // ❌ someone else changed it → loop again → retry
            System.out.println("Conflict! Retrying...");
        }
    }
}
```

---

### compareAndSet — The Heart of Optimistic Locking

```java
balance.compareAndSet(expected, newValue)
//                    ↑          ↑
//             what I read    what I want to set

// Internally does this ATOMICALLY:
if (balance == expected) {
    balance = newValue;
    return true;   // ✅ success
} else {
    return false;  // ❌ someone changed it — retry
}
```

```
Thread-1 reads balance = 1000
Thread-2 reads balance = 1000

Thread-1 → compareAndSet(1000, 900) → ✅ success → balance = 900

Thread-2 → compareAndSet(1000, 800)
         → balance is NOW 900 (not 1000)
         → ❌ FAILS → retry
         → reads balance = 900
         → compareAndSet(900, 700) → ✅ success → balance = 700
```

---

### Using AtomicStampedReference — with Version Number

```java
// Prevents ABA problem
// ABA = value changes 1000→900→1000 — looks same but changed twice

AtomicStampedReference<Integer> balance =
    new AtomicStampedReference<>(1000, 0);
//                                 ↑    ↑
//                              value  version(stamp)

public void withdraw(int amount) {
    while (true) {
        int[] stampHolder = new int[1];
        int currentBalance = balance.get(stampHolder);  // get value + version
        int currentStamp = stampHolder[0];

        int newBalance = currentBalance - amount;

        // update only if BOTH value AND version match
        if (balance.compareAndSet(
                currentBalance, newBalance,
                currentStamp, currentStamp + 1)) {
            // ✅ success — version matched too
            System.out.println("Withdrawn: " + amount);
            return;
        }
        // ❌ version mismatch → retry
    }
}
```

## Optimistic vs Pessimistic — Head to Head

| Feature | Pessimistic | Optimistic |
|---|---|---|
| Locking | Lock **before** work | No lock — verify **after** work |
| Other threads | **BLOCKED** while locked | **Run freely** — may retry at end |
| Java tools | `synchronized`, `ReentrantLock` | `AtomicInteger`, `AtomicLong`, `AtomicReference`, `AtomicStampedReference` |
| Thread blocking | ✅ Yes — threads wait | ❌ No — threads never block |
| Retry logic | ❌ Not needed | ✅ Yes — retry if conflict |
| Performance (low contention) | Slower — unnecessary locking | Faster — no lock overhead |
| Performance (high contention) | Stable | Slower — many retries |
| Risk | Deadlock possible | ABA problem possible |
| CPU usage | Low — blocked threads sleep | Higher — threads spin/retry |

---

## When to Use Which

| Situation | Use | Why |
|---|---|---|
| **Low contention** — threads rarely conflict | **Optimistic** | No lock overhead — faster |
| **High contention** — threads often conflict | **Pessimistic** | Too many retries in optimistic |
| Simple counter / flag | **Optimistic** (AtomicInteger) | CAS is faster than lock |
| Complex multi-step operation | **Pessimistic** | Need all steps locked together |
| Read heavy, write rare | **Optimistic** | Reads never conflict |
| Write heavy, frequent conflicts | **Pessimistic** | Avoid retry storm |
| Bank transfer (debit + credit) | **Pessimistic** | Multi-step — must be atomic |
| Hit counter / view count | **Optimistic** | Simple increment — CAS perfect |

## Full Working Example — Both Together

```java
import java.util.concurrent.*;
import java.util.concurrent.atomic.*;

public class LockingDemo {

    // PESSIMISTIC
    static int pessimisticBalance = 1000;
    static ReentrantLock lock = new ReentrantLock();

    static void pessimisticWithdraw(int amount) {
        lock.lock();
        try {
            if (pessimisticBalance >= amount) {
                pessimisticBalance -= amount;
                System.out.println("Pessimistic: withdrew " + amount
                    + " balance=" + pessimisticBalance
                    + " thread=" + Thread.currentThread().getName());
            }
        } finally {
            lock.unlock();
        }
    }

    // OPTIMISTIC
    static AtomicInteger optimisticBalance = new AtomicInteger(1000);

    static void optimisticWithdraw(int amount) {
        while (true) {
            int current = optimisticBalance.get();
            int updated = current - amount;
            if (updated < 0) return;
            if (optimisticBalance.compareAndSet(current, updated)) {
                System.out.println("Optimistic: withdrew " + amount
                    + " balance=" + updated
                    + " thread=" + Thread.currentThread().getName());
                return;
            }
            System.out.println("Optimistic: conflict, retrying...");
```

| | Deadlock | CAS Retry |
|---|---|---|

| Keeps checking | Same old condition forever | **Fresh new value** each time |
| Will it ever proceed? | ❌ Never — stuck forever | ✅ Yes — next retry succeeds |
| CPU | Blocked / sleeping | Spinning — active |

## When Would It Actually Get Stuck (Livelock)

```
Theoretical worst case — LIVELOCK (not deadlock):

1000 threads all fighting same variable
→ Thread-1 succeeds
→ Thread-2,3,4...999 all fail and retry
→ Thread-2 retries → Thread-3 wins → Thread-2 fails again
→ Thread-2 retries → Thread-4 wins → Thread-2 fails again
→ Thread-2 KEEPS getting unlucky

This is called LIVELOCK — threads are active but one
keeps getting pushed back

BUT in practice:
→ With few threads → resolves in microseconds
→ High contention → use LongAdder instead of AtomicInteger
```
