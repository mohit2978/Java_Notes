## Mutex and Semaphore in Java

Java provides these primitives in `java.util.concurrent` package.

---

### Mutex in Java — `ReentrantLock`

Java doesn't have a class literally named "Mutex", but `ReentrantLock` is the equivalent. The `synchronized` keyword is the simpler built-in option.

**Option 1: `synchronized` (simplest)**
```java
public class Counter {
    private int count = 0;

    public synchronized void increment() {
        // only one thread at a time — mutex behavior
        count++;
    }

    public synchronized int getCount() {
        return count;
    }
}
```

**Option 2: `ReentrantLock` (explicit mutex)**
```java
import java.util.concurrent.locks.ReentrantLock;

public class Counter {
    private int count = 0;
    private final ReentrantLock lock = new ReentrantLock();

    public void increment() {
        lock.lock();           // acquire the mutex
        try {
            count++;           // critical section
        } finally {
            lock.unlock();     // always release in finally!
        }
    }

    public int getCount() {
        lock.lock();
        try {
            return count;
        } finally {
            lock.unlock();
        }
    }
}
```

> Always release in a `finally` block to avoid deadlocks if an exception is thrown.

---

### Semaphore in Java — `Semaphore`

```java
import java.util.concurrent.Semaphore;

public class ConnectionPool {
    // only 3 threads can use the pool at once
    private final Semaphore semaphore = new Semaphore(3);

    public void useConnection(int threadId) {
        try {
            semaphore.acquire();          // decrement; block if 0
            System.out.println("Thread " + threadId + " using connection");
            Thread.sleep(1000);           // simulate work
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        } finally {
            semaphore.release();          // always release!
            System.out.println("Thread " + threadId + " released connection");
        }
    }
}
```

### Full Producer-Consumer Example

This is the classic use case combining both:

```java
import java.util.LinkedList;
import java.util.Queue;
import java.util.concurrent.Semaphore;
import java.util.concurrent.locks.ReentrantLock;

public class ProducerConsumer {

    private final Queue<Integer> buffer = new LinkedList<>();
    private final int CAPACITY = 5;

    private final Semaphore emptySlots = new Semaphore(CAPACITY); // 5 empty slots
    private final Semaphore filledSlots = new Semaphore(0);       // 0 filled slots
    private final ReentrantLock mutex = new ReentrantLock();      // buffer access

    // Producer
    class Producer implements Runnable {
        public void run() {
            for (int i = 0; i < 10; i++) {
                try {
                    emptySlots.acquire();      // wait for empty slot

                    mutex.lock();
                    try {
                        buffer.add(i);
                        System.out.println("Produced: " + i);
                    } finally {
                        mutex.unlock();
                    }

                    filledSlots.release();     // signal item is ready

                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            }
        }
    }

    // Consumer
    class Consumer implements Runnable {
        public void run() {
            for (int i = 0; i < 10; i++) {
                try {
                    filledSlots.acquire();     // wait for an item

                    mutex.lock();
                    try {
                        int item = buffer.poll();
                        System.out.println("Consumed: " + item);
                    } finally {
                        mutex.unlock();
                    }

                    emptySlots.release();      // signal slot is free

                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            }
        }
    }

    public static void main(String[] args) {
        ProducerConsumer pc = new ProducerConsumer();
        Thread producer = new Thread(pc.new Producer());
        Thread consumer = new Thread(pc.new Consumer());
        producer.start();
        consumer.start();
    }
}
```

### Java Cheat Sheet

| Concept | Java Class | Package |
|---|---|---|
| Mutex (simple) | `synchronized` | built-in keyword |
| Mutex (explicit) | `ReentrantLock` | `java.util.concurrent.locks` |
| Semaphore | `Semaphore` | `java.util.concurrent` |
| Read/Write lock | `ReentrantReadWriteLock` | `java.util.concurrent.locks` |

---

### Key Rules to Remember

1. **Always unlock in `finally`** — prevents deadlocks on exceptions
2. **Always release semaphores in `finally`** — prevents resource starvation
3. **Prefer `synchronized`** for simple cases — less boilerplate, harder to misuse
4. **Use `ReentrantLock`** when you need `tryLock()`, timeouts, or fairness control

## Why we use both??

Great question! Let me explain **why we use both** instead of just one.

---

## The Core Problem

In the Producer-Consumer example:
- **Semaphore alone** → can't protect the buffer from simultaneous access
- **Mutex alone** → can't signal "hey, an item is ready!" between threads

**They solve different problems.** That's why we use both.

---

## What Each One Does

```
Mutex  →  "Who can ACCESS the resource?"     (exclusion)
Semaphore → "Is the resource AVAILABLE?"     (signaling / counting)
```

---

## Real-World Use Cases

### Mutex alone — when only 1 thread should touch data
```java
// Bank account — only 1 thread should update balance at a time
ReentrantLock mutex = new ReentrantLock();

void transfer(int amount) {
    mutex.lock();
    try {
        balance -= amount; // critical section — no race condition
    } finally {
        mutex.unlock();
    }
}
```
**Use when:** updating shared variables, writing to a file, modifying a list.

---

### Semaphore alone — when you limit concurrent access
```java
// Max 10 users can download at the same time
Semaphore semaphore = new Semaphore(10);

void download(String file) {
    semaphore.acquire();  // wait if 10 already downloading
    try {
        // download logic
    } finally {
        semaphore.release();
    }
}
```
**Use when:** connection pools, rate limiting, thread pools.

---

### Both together — when you need signaling + safe data access
```java
// Producer-Consumer
// Semaphore → signals when buffer has space / has items
// Mutex     → protects the buffer during read/write

emptySlots.acquire();   // "is there space?" (semaphore)
mutex.lock();           // "let only me write now" (mutex)
try {
    buffer.add(item);
} finally {
    mutex.unlock();
}
filledSlots.release();  // "item is ready!" (semaphore)
```
**Use when:** producer-consumer, pipelines, job queues.

---

## Advantages & Disadvantages

### Mutex
| ✅ Advantage | ❌ Disadvantage |
|---|---|
| Simple — easy to reason about | Only 1 thread at a time (low throughput) |
| Ownership prevents accidental unlocking | Can cause **deadlock** if not careful |
| Safe for protecting shared data | Can cause **starvation** of waiting threads |
| `synchronized` is very easy in Java | `ReentrantLock` is verbose |

### Semaphore
| ✅ Advantage | ❌ Disadvantage |
|---|---|
| Allows N threads concurrently | No ownership — anyone can release (dangerous) |
| Great for signaling between threads | Harder to reason about than mutex |
| Flexible (binary or counting) | Easy to forget `release()` → starvation |
| Solves producer-consumer elegantly | Can be misused as a mutex (bad practice) |

---

## Common Mistakes

### ❌ Using semaphore as a mutex
```java
// WRONG — no ownership, any thread can release it
Semaphore s = new Semaphore(1);
s.acquire();
  // thread B can call s.release() here — bug!
s.release();
```

### ❌ Forgetting finally → deadlock
```java
// WRONG
mutex.lock();
doWork();         // throws exception!
mutex.unlock();   // never reached → deadlock forever
```

### ✅ Always use finally
```java
// CORRECT
mutex.lock();
try {
    doWork();
} finally {
    mutex.unlock(); // always runs
}
```

---

## Simple Decision Guide

```
Need to protect shared data?
        ↓
    → Use MUTEX

Need to limit how many threads run at once?
        ↓
    → Use SEMAPHORE

Need to signal between producer and consumer?
        ↓
    → Use SEMAPHORE (for signaling) + MUTEX (for data access)
```

## One Line Summary

> **Mutex** = lock a door so only you enter.
> **Semaphore** = count how many people are allowed inside.
> **Both together** = count the seats AND lock the door while you sit down.



## Semaphore vs ReentrantLock — Complete Explanation

---

## One Line Each

| | One Line |
|---|---|
| **Semaphore** | Controls how many threads can access a resource **at the same time** |
| **ReentrantLock** | Only **1 thread** at a time can access — but that same thread can lock again without deadlocking itself |

---

## Real Life Analogy

```
Semaphore:
🅿️ Parking Lot with 3 slots
→ 3 cars can park simultaneously
→ 4th car waits outside
→ when 1 car leaves → 4th car enters

ReentrantLock:
🚽 Single toilet with a key
→ Only 1 person can use at a time
→ Same person can re-enter (reentrant)
→ Others wait outside until key is returned
```

---

## Semaphore — Explained Clearly

```java
Semaphore semaphore = new Semaphore(3);
// 3 = number of permits (slots)
```

### How it works

```
Semaphore permits = 3

Thread1 → acquire() → permits = 2  ✅
Thread2 → acquire() → permits = 1  ✅
Thread3 → acquire() → permits = 0  ✅
Thread4 → acquire() → permits = 0  ❌ BLOCKED — waits

Thread1 → release() → permits = 1
Thread4 → acquire() → permits = 0  ✅ now allowed in
```

### Code

```java
Semaphore semaphore = new Semaphore(3); // 3 threads allowed at once

public void accessResource() {
    try {
        semaphore.acquire();        // take 1 permit
        // do work — up to 3 threads can be here simultaneously
        System.out.println(Thread.currentThread().getName() + " working");
        Thread.sleep(2000);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    } finally {
        semaphore.release();        // return the permit
    }
}
```

---

## ReentrantLock — Explained Clearly

```java
ReentrantLock lock = new ReentrantLock();
// Only 1 thread allowed at a time
```

### Why "Reentrant"?

```
❌ Normal lock problem (deadlock):
Thread1 holds lock → calls method2 → method2 also needs same lock
→ Thread1 waits for itself → DEADLOCK forever

✅ ReentrantLock solution:
Thread1 holds lock → calls method2 → method2 needs same lock
→ Thread1 already owns it → allowed in → no deadlock
→ Lock count increases (2) → must release twice
```

### Code

```java
ReentrantLock lock = new ReentrantLock();

public void method1() {
    lock.lock();           // lock count = 1
    try {
        System.out.println("method1");
        method2();         // same thread calls method2
    } finally {
        lock.unlock();     // lock count = 0
    }
}

public void method2() {
    lock.lock();           // same thread → lock count = 2 (allowed!)
    try {
        System.out.println("method2");
    } finally {
        lock.unlock();     // lock count = 1
    }
}
// After both unlocks → lock count = 0 → other threads can enter
```

---

## Key Difference — How Many Threads

```
Semaphore(3):                    ReentrantLock:

Thread1 ✅ working               Thread1 ✅ working
Thread2 ✅ working               Thread2 ❌ waiting
Thread3 ✅ working               Thread3 ❌ waiting
Thread4 ❌ waiting               Thread4 ❌ waiting

→ 3 at a time                   → 1 at a time
```

---

## Feature Comparison Table

| Feature | Semaphore | ReentrantLock |
|---|---|---|
| How many threads allowed | **N threads** (you decide) | **Only 1 thread** |
| Reentrant (same thread re-lock) | ❌ No — will deadlock itself | ✅ Yes — safe |
| Who can release | **Any thread** can release | Only the **thread that locked** it |
| Fairness option | ✅ `new Semaphore(3, true)` | ✅ `new ReentrantLock(true)` |
| tryLock / tryAcquire | ✅ `tryAcquire()` | ✅ `tryLock()` |
| Use case | Limit concurrent access | Mutual exclusion (critical section) |
| Ownership concept | ❌ No owner | ✅ Has owner (the locking thread) |
| Can check lock status | ❌ No | ✅ `isLocked()`, `isHeldByCurrentThread()` |
| Condition variables | ❌ No | ✅ `lock.newCondition()` |

---

## Who Can Release — Important Difference

```java
// SEMAPHORE — any thread can release
Semaphore s = new Semaphore(1);

Thread1 → s.acquire()   // Thread1 takes permit
Thread2 → s.release()   // Thread2 releases it ✅ perfectly valid
                         // Semaphore does not care who releases

// REENTRANTLOCK — only owner can unlock
ReentrantLock lock = new ReentrantLock();

Thread1 → lock.lock()    // Thread1 owns the lock
Thread2 → lock.unlock()  // ❌ throws IllegalMonitorStateException
                          // only Thread1 can unlock
```

---

## tryLock and tryAcquire — Non Blocking

```java
// ReentrantLock — tryLock
ReentrantLock lock = new ReentrantLock();

if (lock.tryLock()) {           // does not block — returns true/false immediately
    try {
        // got the lock — do work
    } finally {
        lock.unlock();
    }
} else {
    // could not get lock — do something else
    System.out.println("Lock not available, skipping");
}

// Semaphore — tryAcquire
Semaphore s = new Semaphore(3);

if (s.tryAcquire()) {           // does not block — returns true/false
    try {
        // got permit — do work
    } finally {
        s.release();
    }
} else {
    System.out.println("No permit available, skipping");
}
```

## Fairness Mode

```java
// Without fairness — random thread gets lock (can cause starvation)
ReentrantLock lock = new ReentrantLock();
Semaphore s = new Semaphore(3);

// With fairness — FIFO order — longest waiting thread gets lock first
ReentrantLock fairLock = new ReentrantLock(true);
Semaphore fairSemaphore = new Semaphore(3, true);
```

| Mode | Behavior | Performance |
|---|---|---|
| Unfair (default) | Any waiting thread can get lock | Faster |
| Fair | Thread that waited longest gets it first | Slower but no starvation |

---

## When to Use Which

| Situation | Use |
|---|---|
| Only 1 thread should access at a time | **ReentrantLock** |
| Same thread calls nested locked methods | **ReentrantLock** (reentrant) |
| Limit DB connections to max 5 at a time | **Semaphore(5)** |
| Limit API calls to max 10 concurrent | **Semaphore(10)** |
| Thread pool size control | **Semaphore** |
| Critical section protection | **ReentrantLock** |
| Producer-Consumer with conditions | **ReentrantLock** + `newCondition()` |
| Any thread can signal/release | **Semaphore** |

|---|---|---|---|
| Threads allowed | 1 | 1 | N |
| Reentrant | ✅ | ✅ | ❌ |
| tryLock | ❌ | ✅ | ✅ |
| Fairness | ❌ | ✅ | ✅ |
| Condition variables | ❌ | ✅ | ❌ |
| Manual unlock needed | ❌ | ✅ | ✅ |
| Any thread release | ❌ | ❌ | ✅ |
| Ease of use | Easy | Medium | Medium |
