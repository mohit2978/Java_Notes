# Method Reference

Whenever you have a lambda expression whose only job is to take an incoming parameter and instantly pass it into an existing method, you can use a Method Reference (::) to make the code even cleaner.


### How the Syntax Works
The syntax is always: `ClassName::methodName` eg. `String::length`

Notice that there are no parentheses after length.
Just like we have seen `() -> { f() }`, you are not executing the `length()` method right now. You are simply passing a reference to the method (the "recipe") so that Java can call it later when it needs to.

### . How Java figures it out
When you use `String::length` inside something like a Stream, Java is smart enough to infer what is happening.

If you have a list of strings and you want to convert them to a list of their lengths, you use the map() intermediate operation.

As we discussed earlier, map() requires a `Function<T, R>` (something that takes an input and returns a result).


```java
List<String> names = List.of("Alice", "Bob", "Charlie");

// Java knows 'names' is a stream of Strings.
// It takes each String, passes it as the hidden 'this' parameter to length(), 
// and returns the Integer.
names.stream()
     .map(String::length) 
     .forEach(System.out::println); // Prints 5, 3, 7
```


Notice `System.out::println` at the end? That is also a method reference! It is shorthand for `name -> System.out.println(name)`).



| Type | Syntax | Example | Equivalent Lambda |
| :--- | :--- | :--- | :--- |
| Static Method | `Class::staticMethod` | `Math::max` | `(a, b) -> Math.max(a, b)` |
| Instance Method of an Object | `instance::method` | `System.out::println` | `x -> System.out.println(x)` |
| Instance Method of a Class | `Class::method` | `String::length` | `s -> s.length()` |
| Constructor | `Class::new` | `ArrayList::new` | `() -> new ArrayList<>()` |

Q--> Math::max how java knows about parameters??

This is the exact moment where Java's compiler looks like absolute magic.

When you write Math::max, you aren't telling Java what the parameters are. Java figures it out by looking at the "socket" you are trying to plug Math::max into.

This process is called Target Typing (or Type Inference). Java doesn't look at the method reference first; it looks at the destination first.

Here is a step-by-step look inside the compiler's brain to see how it connects the dots.

###  Step 1: Looking at the Destination (The Socket)
Imagine you assign Math::max to a functional interface variable, or pass it into a Stream method like reduce().

```java
// We are plugging Math::max into a BinaryOperator socket
BinaryOperator<Integer> maxFinder = Math::max;
```
The compiler stops and looks at the left side of the equals sign: `BinaryOperator<Integer>`.
It asks: "What are the strict rules for a BinaryOperator?"

Rule: It must take two inputs of type T.

Rule: It must return one output of type T.

Since we specified `<Integer>`, the compiler knows the hidden abstract method looks exactly like this: Integer apply(Integer a, Integer b);



### Step 2: Looking at the Method Reference (The Plug)
Now the compiler looks at the right side: `Math::max`.
It goes into the `Math` class source code and searches for a method named `max`.
It finds several versions of it (method overloading):

* `max(long a, long b)`
* `max(float a, float b)`
* `max(int a, int b)`

### Step 3: The Matchmaker
The compiler plays matchmaker. It compares the socket (`BinaryOperator<Integer>`) with the plug (`Math::max`).

It asks: *"Does the `Math` class have a `max` method that takes two Integers (`int`s) and returns one Integer (`int`)?"*

Yes, it does! (`public static int max(int a, int b)`). Because the inputs and the return type match the required shape perfectly, the compiler secretly wires the parameters together for you.

---

### What happens if it doesn't match?
If you try to plug `Math::max` into the wrong shaped socket, the compiler immediately throws an error.









```java
// ERROR: Does not compile!
Consumer<Integer> myConsumer = Math::max;
```

Why does this fail?

The compiler checks the `Consumer<Integer>` socket. Rule: It takes one Integer, and returns void.

It checks the Math::max plug. It requires two parameters, and it returns a value.

The shapes don't match. The compiler says, "I don't know how to pass one parameter into a method that requires two," and the code breaks.

### The Summary
Java knows about the parameters because the Functional Interface dictates them.

When you use a Method Reference, you are making a promise to the compiler: "I promise that the method I am referencing perfectly matches the inputs and outputs that this functional interface expects." If you keep that promise, Java handles the parameters invisibly.
